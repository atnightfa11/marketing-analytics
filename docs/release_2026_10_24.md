# Metrics And Delivery Corrections

## Scope

- Engagement: bounce means one pageview with no conversion/revenue interaction. Measured visit duration runs from first to last interaction, not just between pageviews. KPI and filtered rollups use the same implementation. No inferred dwell time or multiplier is added.
- Reddit: web and Android app referrals normalize to Reddit / Organic Social, preserving explicit paid attribution.
- Reporting: new events, daily identity rotation, and completed-day forecast selection follow the active site timezone. Dayparting uses event time and the reporting timezone, not each visitor's browser timezone.
- Delivery: initial visits send immediately; later batches send after roughly one second. Solo/Standard no longer enter the random shuffle-delay path. Network failures retry automatically with stable event nonces and fresh request nonces. Page-exit events do not wait for an earlier request, and persisted back/forward-cache restores record a pageview.
- The SDK build refreshes the checked-in hosted bundle before dashboard deployment.

## What The Investigation Established

For the September 25 through October 22 comparison, all 28 Neurotypical Translator reporting days had successful reducer watermarks. This was not a missing-day or Solo DP-noise problem.

Production was using the default shuffle delay of up to 120 seconds, while the SDK aborted requests after 20 seconds. The SDK also normally waited three minutes to send events and requeued failed batches without scheduling a retry. These are collection reliability defects, especially relevant to short mobile visits. They do not prove exactly how many of the historical missing pageviews they caused; older raw processing records have been purged. A client timeout also does not always mean the server failed to accept an event.

Self-referral exclusions, privacy signals, browser blocking, identity definitions, and differing conversion configurations can still produce legitimate differences from another tracker. This release does not calibrate counts to Plausible, weaken DNT/GPC handling, or manufacture missing events.

## Deploy Order

1. Apply Alembic revision `2026_10_24_reporting_timezone` using the production database connection and the updated migration files. Verify that Alembic reports this single head. The migration was tested against a disposable local PostgreSQL instance, not production.
2. Deploy the matching API and worker code together, before the scheduled cutover. The migration chooses a site-local midnight at least 24 hours after it runs for existing non-UTC sites. If rollout must be postponed beyond that, reschedule the pending cutovers before ingestion switches. Do not leave mixed API versions collecting across the boundary.
3. Run `npm run build` in `client/`, then build and deploy `dashboard/`. The client build refreshes `dashboard/public/validanalytics.global.js` and its source map. Existing sites loading the hosted URL do not need to reinstall the snippet. Sites hosting their own copy need the new bundle.
4. Let the worker reduce retained raw days and refresh forecasts. Only rebuild days whose full raw processing rows are still available and whose watermark does not record a prior purge. Do not delete old rollups to force a rebuild.
5. Verify settings show the pending/active timezone, then check the first completed local day for correct date boundaries, pageviews, engagement, and Reddit attribution. Repeat comparisons using the same date range, reporting timezone, hostname scope, and event definitions.

## History And Privacy

Historical aggregate date labels and values are preserved. Older UTC daily totals cannot be shifted accurately into local days after their raw events have been purged. A timezone transition can produce one shorter or longer reporting day; subsequent days follow local midnight, including DST. No claim is made that a historical comparison window has been retroactively repaired.

The server overwrites the processing timestamp/timezone fields from validated event timing and site configuration. These fields, daily HMACs, and raw payloads remain subject to the existing guarded purge. No new persistent browser identity or persistent event queue is introduced.

Reducer watermark compatibility remains unchanged so already-purged days remain readable. Engagement/attribution semantics improve when a day is newly reduced or safely rebuilt; existing durable history is not invalidated merely because the code changed.

## Verification

Regression coverage includes measured engagement, conversion-only engagement after a pageview, same-timestamp pageviews, rolling-session page filters, Reddit app attribution, DST/local midnight, daily identity rotation, forecast exclusion of the partial local day, retry deduplication, migration/history preservation, and the hosted SDK's mobile-sized browser delivery path. Browser lifecycle tests simulate pagehide and persisted pageshow events; they are not a guarantee of delivery after a real device force-quit.

Local verification on October 24: 172 backend tests, 12 isolated PostgreSQL tests, 36 SDK tests, 4 dashboard unit tests, and 17 Cypress browser tests passed. Backend/client/dashboard lint, dashboard typechecking, and SDK/dashboard production builds passed. Existing FastAPI/Pydantic deprecation warnings and the dashboard's large-bundle warning remain.
